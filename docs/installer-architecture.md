# Durable installer architecture

Rasta.app Library handles connection installation, updates, recovery and removal. The per-host packages contain the engine and the shared reading panel.

## Installation and recovery

Library verifies the package selected for the host before preparing a signed staging copy. The installed host stays open until the user selects Launch. The eight connections share the installer workflow and keep separate app state, backups, compatibility checks and vendor integrity settings.

`bin/lib/host-compatibility.js` owns local capability checks. `bin/lib/installer-policy.js` selects an eligible release. `bin/lib/gui-updates.js` owns the authenticated staging and commit transaction. A verified package still checks the installed host and signs its staged replacement before Launch.

Library detects vendor replacement from the saved bundle fingerprint. Recovery reuses a compatible, verified package or obtains one through the selected signed feed. Upgrading a connection retires its owned legacy recovery copy and update watcher.

### Keychain access for T3, Claude and ZCode

When the user chooses Launch, the package tool verifies the staged code and the original publisher's signed bundle. It keeps the designated requirement used by Squirrel for official updates. It checks the host's exact Safe Storage service in the login keychain for accounts named either after the app or after the app with the ` Key` suffix. For ZCode it also checks the exact `ZCode Credential Encryption` service, whose account names are generated by the host. For each matching item, it verifies the official app's existing grant and adds a trusted application requirement tied to the staged app's identifier and code directory hash. It preserves the existing permissions. macOS handles authorization without giving Rasta the item value or the user's password.

The permission applies to the authorized app build on ordinary launches from Finder and the Dock. A later Rasta build can require macOS authorization for a new hash. Earlier grants remain scoped to their exact builds so rollback can still use them. If authorization fails, Library stops before closing or replacing the host. A whole-bundle vendor update requires the existing Library recovery flow to restore reading support.

## Download aliases

After publication, Latest provides `Rasta-Apple-Silicon.dmg`. Signed update feeds reference
immutable versioned files. Promotion checks drafts and public downloads before
advancing Latest.

## Update handoff and support migration

Each authenticated job downloads into its own directory. A newer release
discovered during handoff leaves the parent archive available to its worker.
The worker stages the verified host and checks compatibility while the original
app and support directory remain active. After Launch and normal exit it moves
mutable state to the canonical support paths and installs the staged bundle.
A failed commit restores the prior paths and metadata.

After the new renderer confirms startup and older workers finish, the canonical
helper retires the temporary path bridge and superseded runtimes. It checks the
exact host, version, readiness and destination before cleanup. Failed takeover
or an existing conflicting directory preserves the bridge and backup for
recovery. The support migration tests cover rollback, cancellation, parallel
handoff and paths containing spaces.

## Acceptance

Keep the previous Rasta connection installed until the user begins its update in Library. Use the signed local candidate and record the offered version, completed upgrade, displayed version and working app for each target in the candidate. Record the closed-panel update indicator when the host provides it. Verify staging on compatible older and newer host versions, signature and network failures, and rejection of incompatible hosts before installation. Automated fixtures do not substitute for user observations.

Native acceptance, public clean-install checks, production panel upgrades and real vendor-update recovery are distinct records. Public promotion requires explicit authorization and acceptance of the exact candidate. The agent never closes or replaces the installed original host.
